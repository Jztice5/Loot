# Loot 时间上下文模型评审

## 1. 评审范围

- 三类上下文是否互斥且覆盖任务生命周期。
- 是否需要新增目录或复制现有文档。
- 任务状态迁移是否能被未来 Codex 执行。
- 稳定架构与时间上下文是否职责清楚。

## 2. 结论

模型成立。过去式、现在进行时和未来规划分别解决证据、当前事实和尚未发生事项；现有
log/review、memory、planning 已能承载，无需新增三套目录。

architecture、AGENTS 和 runbooks 作为跨时间稳定上下文存在，避免把架构规则错误归为
某一次历史或当前任务状态。

## 3. 已确认规则

- Planned/Deferred 开始执行时转为 In Progress，并在 memory 建立当前焦点链接。
- 状态转换在 planning 原需求条目完成，memory 只维护项目当前快照和链接。
- Done/Rejected/Superseded 进入过去式，必须有结果、原因或证据链接。
- 历史验证不能表述为当前机器已复验。
- 未来规划不能使用已经实现或通过的措辞。
- 已结束事项从 memory 活跃区移除，通过季度索引保持可追溯。
- 跨任务复用的结论晋升到 architecture、AGENTS 或 runbooks。

## 4. 保留风险

- 自动检查只能确认模型入口存在，无法完全判断自然语言是否误用时态。
- 第一次真实跨季度 carryover 仍需人工复核 Planned、In Progress 和历史归档状态。

## 5. 一句话结论

三类时间上下文形成 `未来规划 -> 现在进行时 -> 过去式` 的闭环，稳定规则在闭环之外沉淀并持续约束后续任务。
