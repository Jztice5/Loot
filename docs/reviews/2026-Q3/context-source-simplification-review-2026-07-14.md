# Loot 动态上下文单一事实源评审

## 1. 评审范围

- `development/memory.md`、季度 planning 和 development log 的动态信息边界。
- “下一步”“推进顺序”和历史遗留事项是否存在重复或冲突。
- 自动检查与项目 Skill 是否会持续制造重复文档。

## 2. 发现

- 季度开发计划、需求管理、memory 和规划总览同时维护下一步，已经出现顺序漂移。
- 历史 log 使用“后续”或“下一环节”标题，容易把当时判断误读成当前指令。
- 原规则同时要求“下一步在 memory”和“推进顺序在 planning”，语义边界不够可执行。
- 自动检查强制每季度创建开发计划，使结构性重复无法自然消失。

## 3. 结论

- 需求管理独占需求状态、依赖、验收标准和计划队列。
- memory 只保存当前执行、阻塞、恢复点和当前验证基线。
- development log 只保存过去式证据；未决判断必须标成“历史快照”。
- 规划总览只做导航，不复制当前焦点。
- 退役季度流水式开发计划；复杂需求确需实施计划时，建立与 REQ 绑定的专题计划。

本结论取代[上下文文档季度化评审](quarterly-context-organization-review-2026-07-14.md)中
“每季度必须维护开发计划”的规则，也取代
[设计分层校对备忘录](loot-design-layering-review-2026-07-10.md)中把完整未完成事项和下一步
放入 memory 的规则；旧评审保留为历史记录。

## 4. 验证

- 项目 Skill 与全局 Codex 镜像均通过 validator，SHA-256 一致。
- `make check` 通过：context check、`compileall` 和 41 个 unittest 全部成功。
- context check 统计 45 个 Markdown 文件、116 个本地链接，memory 由 105 行降至 48 行。
- 自动检查会拒绝季度流水式开发计划和历史 log 的动态计划标题。
- 人工扫描未发现 memory、规划总览或独立开发计划复制完整需求队列。

## 5. 一句话结论

当前执行看 memory，后续队列看需求管理，历史判断看 log；三者不再共同维护“下一步”。
