用户场景：

- Provider、进程或数据库短暂失败后，系统可以重试或恢复，不产生重复决策事实。

目标：

- 调度 ACTIVE MonitoringSubscription，并复用 REQ-0013 的确定性应用服务执行 Crypto 链路。
- 建立持久化 Run 账本、阶段状态、重试预算、租约或并发锁，以及中断后的恢复规则。
- 以 `subscription + bar close time + workflow version` 建立稳定运行身份，覆盖重复投递。
- 保证无 Candidate 是正常业务结果，而不是失败或无限重试原因。

影响范围：

- 领域：Platform Monitoring Runtime、Crypto Provider 和现有决策链路。
- 模块：application worker、scheduler/runner、persistence repositories、运行 CLI。
- 表：监控运行账本及必要的尝试记录；沿用现有决策链、inbox 和 outbox 表。
- 事件：运行已调度、成功、无候选、失败、等待重试和恢复事件或等价审计事实。
- 状态机：Run 生命周期；Signal 仍只允许由现有 Signal workflow 写入。

非目标：

- 初版不引入 Redis、Kafka、Celery、Kubernetes 或 OKX WebSocket。
- 不实现多市场 Session 调度、高频轮询、自动横向扩容或 UI 运维台。

验收：

- Provider 临时失败按预算退避重试；永久失败进入可观测终态，不阻塞其他订阅。
- PAUSED 或 ARCHIVED WatchItem 不会启动新 Run，运行前配置版本变化按明确规则放弃或重建。
- 覆盖成功、无 Candidate、重复调度、依赖失败、重试耗尽、进程中断和恢复测试。

### REQ-0016：Crypto Alert Center 最小闭环

状态：Planned

依赖：REQ-0018。

用户场景：

- Crypto Signal 发生值得关注的状态变化时，用户收到一次可追踪提醒，而不是每轮重复命中都提醒。
- 通知渠道短暂失败时可以独立重试，不影响已经提交的 Signal 事实。

目标：

- 消费 Signal 状态变化 Outbox，形成持久化 `AlertEvent` 和投递记录。
- 实现基于用户、Signal、目标状态、迁移版本和渠道的去重键。
- 实现最小优先级、冷却、投递重试、ACK 和 IGNORE 生命周期。
- 提供 Notifier 端口、FakeNotifier 测试适配器和一个可配置的真实可见渠道。

影响范围：

- 领域：Alert，不把通知策略写入 Crypto Domain 或 Signal State Machine。
- 模块：alert policy、outbox consumer、notifier adapters、persistence。
- 表：`alert_events`、`alert_deliveries`，以及必要的 inbox/outbox 记录。
- 事件：Alert 请求、已抑制、投递成功、投递失败、已确认和已忽略。
- 状态机：Alert/Delivery 生命周期；通知结果不能反向修改 Signal 状态。

非目标：

- 不实现完整 Dashboard、移动端、复杂模板中心或多渠道路由平台。
- 不基于 Agent/LLM 改写提醒事实、优先级或 Signal 状态。
- 不实现自动下单或把提醒动作解释为交易指令。

验收：

- 同一 Signal 迁移重复消费只形成一个 Alert；不同迁移版本可形成新的提醒事实。
- 冷却只抑制通知，不丢失 SignalTransition 和 Alert 审计；CRITICAL 覆盖规则有确定性测试。
- 通知失败独立重试且不回滚 Signal；重试耗尽后保留失败原因和人工恢复入口。
- FakeNotifier 覆盖集成测试；真实渠道、凭据加载和脱敏规则在实施计划开始前确定。
- 覆盖成功、冷却抑制、重复消费、渠道失败、恢复、ACK 和 IGNORE 路径。

## 2026-07-14 设计校准

状态：Done

结论：

- Policy 前对象统一命名为 `DecisionProposal`。
- Policy Gate 对每个 Proposal 记录 `PolicyEvaluation`。
- 只有 `APPROVED` 才签发 `DecisionTicket`。
- Signal State Machine 只消费 Policy 后的 DecisionTicket。
- Position 只影响 Policy、优先级和提醒语义，不改变市场结构信号的真假。
- 当前代码仍把 Policy 前对象实现为 `DecisionTicket`，必须在 REQ-0007 前完成契约迁移。
- Snapshot identity 必须绑定完整窗口；闭合 K 线必须满足时间真实性。
- Policy DEFERRED 必须允许在新上下文中追加评估，不能被幂等键永久阻塞。
- Ticket 必须绑定并验证 Signal 与业务上下文版本，状态机不能信任可任意构造的对象。
- 初始 Signal 不需要 Ticket；终态后使用新 generation，不重置旧实例。

### REQ-0007：Crypto Candidate 到 Signal 授权链路最小串联

状态：Done

目标：

- 将 Crypto Candidate 转成稳定 `EvidenceSet` 和 `DecisionProposal`。
- 将 Candidate.direction 原样贯穿 Proposal、Ticket、SignalInstance 和 SignalEvent。
- 通过最小 Policy Gate 生成三态 `PolicyEvaluation`，批准时签发唯一
  `DecisionTicket`。
- 只允许授权事实仓库中可验证的 `DecisionTicket` 调用 Signal State Machine。

交付：

- Policy 前 `DecisionProposal`、三态 `PolicyEvaluation` 和 Policy 后
  `DecisionTicket` 契约，旧 Ticket 语义已删除。
- `DeterministicDecisionBuilder` 和 Crypto 最小 `CryptoPolicyGate`。
- `AuthorizationRepository` / `PolicyAuthorizationRepository` 端口及 Phase 0 内存适配器。
- Signal 幂等初始化、generation 管理和授权链校验后的状态迁移。
- direction-aware、可追踪 Candidate/Proposal/Evaluation/Ticket/Snapshot 的 SignalEvent。

验收：

- 同一 Candidate 和版本上下文产生稳定 Evidence/Proposal identity。
- REJECTED、DEFERRED 不签发 Ticket；DEFERRED 在数据上下文恢复后可追加 APPROVED 评估。

### Crypto 信号准确性优化观察项（已晋升）

状态：Superseded by REQ-0018

当前 `crypto.structure-breakout.v1` 的 3 根参考 K 线加 1 根收盘突破规则，是用于验证
Provider、PreFilter、Policy、Signal 和持久化链路的可解释基线。REQ-0013 的 demo、Golden
Case 和工程测试只证明系统按既定契约正确执行，不证明 LONG/SHORT 信号具有统计准确性。

该观察项已在 2026-08-04 晋升为 `REQ-0018`。以下前置条件和优化顺序保留为需求来源，当前
状态、依赖、验收标准和执行顺序以 `REQ-0018` 原条目为准，不再由本观察项发布计划指令。

原始触发条件：

1. MarketBar、MarketSnapshot 和必要 Candidate 输入可以持久化，并能从事实源完整恢复。
2. 最小 Replay 能使用相同快照和规则版本复现 Candidate、Evidence 与 Signal 结果。
3. 已定义固定观察窗口及 MFE、MAE、假突破、先止损/先目标、达到 1R/2R 时间等结果标签。
4. Data Quality Gate 能真实识别 K 线缺失、重复、时间断档、行情延迟和数据修正，而不是固定
   传入 `data_quality_ready=True`。
5. 首轮研究样本至少包含 200 个已标注 Candidate，且 LONG、SHORT 各不少于 50 个；该阈值
   只允许启动探索，不代表生产置信度，正式验收样本量需在评测设计中按置信区间重新计算。

满足条件后按以下顺序优化并用 Replay 对照基线：

1. 先统计基线的命中率、覆盖率、假突破率、MFE/MAE 和期望值，并按方向、波动率和市场状态分层。
2. 单变量比较突破幅度或 ATR 阈值、成交量确认、4H 趋势加 1H 触发、回踩确认。
3. 只有确定性增强有可复现实证后，再评估 funding/OI/liquidation、新闻或 Agent 特征。
4. 任一增强必须保留旧规则版本和相同样本对照，不能只比较少量成功案例。
